1. 전체 그림

이 서비스는 Worker 하나로 구성됩니다. Worker는 정적 페이지(검색 UI와 저장 팝업)를 제공하고, /api/* 경로로 들어오는 요청을 처리하며, 한 시간마다 Cron으로 깨어나서 밀린 임베딩 작업을 처리합니다.

2. D1 스키마

테이블은 bookmarks 하나뿐입니다. 북마크의 텍스트와 벡터 사본, 임베딩 진행 상태를 한 행에 모두 담습니다.

-- migrations/0001_init.sql
CREATE TABLE bookmarks (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  url          TEXT    NOT NULL UNIQUE,
  title        TEXT    NOT NULL DEFAULT '',
  description  TEXT    NOT NULL DEFAULT '',   -- meta description
  memo         TEXT    NOT NULL DEFAULT '',
  content      TEXT    NOT NULL DEFAULT '',   -- 본문 앞부분 (~2,000자), 재임베딩용
  created_at   INTEGER NOT NULL,              -- 서버 시각, Unix ms

  embed_status   TEXT    NOT NULL DEFAULT 'pending'
                 CHECK (embed_status IN ('pending', 'embedded', 'indexed')),
  embed_model    TEXT,                        -- '@cf/baai/bge-m3'
  embedding      BLOB,                        -- Float32 × 1024 = 4,096 bytes
  embed_attempts INTEGER NOT NULL DEFAULT 0,  -- 현재 단계의 연속 실패 횟수
  embed_error    TEXT                         -- 마지막 실패 메시지
);

CREATE INDEX idx_bookmarks_created_at ON bookmarks (created_at);
CREATE INDEX idx_bookmarks_unfinished ON bookmarks (embed_status)
  WHERE embed_status != 'indexed';

컬럼별 설계 이유

컬럼설계 이유
idVectorize의 벡터 ID로도 사용합니다("42"처럼 문자열로 변환). AUTOINCREMENT를 붙인 이유는 아래 주의 상자에서 설명합니다.
urlUNIQUE 제약으로 중복 저장을 데이터베이스 수준에서 거부합니다. 애플리케이션 코드에서 먼저 확인하더라도, 동시에 두 번 저장하는 경우까지 막아 주는 것은 이 제약입니다.
title, description, memo임베딩 입력이면서 키워드 검색 대상입니다.
content임베딩 입력이지만 키워드 검색에서는 제외합니다. 본문에 우연히 들어간 단어 때문에 검색 결과가 지저분해지는 것을 막기 위해서입니다. 그래도 보관해 두는 이유는 나중에 모델을 바꿨을 때 원문 페이지 없이 다시 임베딩하기 위해서입니다.
created_at정수(Unix ms)로 저장하면 날짜 범위 필터가 단순한 숫자 비교가 되고, 인덱스도 효율적으로 동작합니다. Unix ms는 시간대와 무관한 절대 시각이므로, KST 변환은 API의 입출력에서만 합니다. 응답에는 2026-09-26T19:58:00+09:00 형식의 문자열을 함께 담고, 날짜 필터의 2026-09-26은 KST 하루(00:00~23:59)로 해석합니다.
embed_status임베딩 파이프라인의 진행 단계를 기록합니다. 다음 절에서 자세히 설명합니다.
embed_model어떤 모델로 만든 벡터인지 기록합니다. 모델을 바꾸면 이 값이 다른 행만 골라서 다시 임베딩합니다.
embedding벡터 사본입니다. Float32Array의 바이트를 그대로 저장하므로 북마크 하나에 정확히 4,096바이트가 듭니다. D1만 내보내면 벡터까지 옮겨지고, Vectorize는 이 값으로 AI 호출 없이 재구축할 수 있습니다.
embed_attempts현재 단계에서 연속으로 실패한 횟수입니다. 5회에 도달하면 Cron이 더 이상 시도하지 않고, 단계가 성공하면 0으로 초기화합니다.
embed_error실패 원인을 남겨서 웹 UI나 SQL로 확인할 수 있게 합니다.
왜 AUTOINCREMENT가 필요한가 SQLite의 기본 INTEGER PRIMARY KEY는 가장 큰 ID의 행을 지우면 그 번호를 다시 사용할 수 있습니다. 그런데 북마크를 삭제할 때 D1 삭제는 성공하고 Vectorize 삭제가 실패하면, Vectorize에는 옛 벡터가 "42"라는 ID로 남아 있게 됩니다. 이때 새 북마크가 42번을 다시 받으면 옛 벡터가 새 북마크의 것처럼 보이는 오류가 생깁니다. AUTOINCREMENT는 한 번 쓴 번호를 절대 재사용하지 않으므로 이 문제를 원천적으로 막습니다.
인덱스 두 개의 역할 idx_bookmarks_created_at은 최신순 정렬과 날짜 범위 필터를 빠르게 합니다. idx_bookmarks_unfinished는 부분 인덱스(partial index)라서 아직 인덱싱이 끝나지 않은 소수의 행만 담습니다. 그래서 Cron이 "처리할 항목"을 찾을 때 전체 테이블을 훑지 않습니다.

키워드 검색 쿼리

LIKE 검색은 인덱스를 쓰지 못하므로 전체 행을 훑습니다. 수천 개 규모에서는 충분히 빠르지만, 목록을 조회할 때 4KB짜리 embedding 컬럼은 절대 읽지 않도록 필요한 컬럼만 명시합니다.

SELECT id, url, title, memo, created_at, embed_status
FROM bookmarks
WHERE (title LIKE ?1 ESCAPE '\' OR memo LIKE ?1 ESCAPE '\'
       OR description LIKE ?1 ESCAPE '\')        -- content는 검색 제외
  AND created_at BETWEEN ?2 AND ?3
ORDER BY created_at DESC
LIMIT ?4 OFFSET ?5;

검색어에 들어 있는 %와 _는 \%, \_로 이스케이프합니다. 그렇지 않으면 "100%"를 검색했을 때 의도하지 않은 결과가 나옵니다. 참고로 SQLite의 LIKE는 영문 대소문자를 구분하지 않고, 한글에는 대소문자 개념이 없으므로 따로 처리할 필요가 없습니다.

3. 임베딩 상태 전이

저장은 "D1에 텍스트 저장 → 임베딩 → D1에 벡터 기록 → Vectorize 삽입" 순서로 진행됩니다. 각 단계는 따로 실패할 수 있으므로, 행마다 어디까지 끝났는지를 embed_status에 기록합니다.

이렇게 단계를 나누면 처리 로직 하나(pipeline.ts)로 세 가지 상황을 모두 다룰 수 있습니다.

  • 새 북마크: 저장 요청에 응답한 직후 ctx.waitUntil()로 파이프라인을 실행합니다. 따라서 팝업은 임베딩을 기다리지 않고 바로 닫힙니다.
  • 실패한 항목: 매시간 Cron이 embed_status != 'indexed' AND embed_attempts < 5인 행을 최대 N개 가져와서 파이프라인에 다시 넣습니다. 5회 연속 실패한 항목은 웹 UI에 "임베딩 실패"로 표시되고, UPDATE bookmarks SET embed_attempts = 0 WHERE id = ?로 횟수를 되돌리면 다시 시도합니다.
  • Vectorize 재구축: SQL 한 줄(UPDATE bookmarks SET embed_status = 'embedded' WHERE embed_status = 'indexed')로 상태를 되돌리면, Cron이 D1의 벡터 사본을 Vectorize에 다시 넣습니다. 임베딩을 다시 계산하지 않으므로 AI 비용이 들지 않습니다.
임베딩 입력 텍스트 제목\n메모\ndescription\n본문 순서로 이어 붙입니다. 메모를 앞쪽에 두는 이유는 내가 직접 쓴 설명이 페이지 본문보다 의도를 더 정확하게 나타내기 때문입니다. URL은 넣지 않습니다.

4. Vectorize 인덱스

npx wrangler vectorize create bookmarks --dimensions=1024 --metric=cosine
  • 차원 1024, cosine 거리: bge-m3의 출력에 맞춘 값입니다. 인덱스를 만든 뒤에는 바꿀 수 없습니다.
  • 메타데이터 없음: 날짜 필터는 키워드 검색에만 적용하기로 했으므로, 벡터에는 ID와 값만 넣습니다. 제목 같은 표시용 정보는 D1에서 가져옵니다.
  • 유사 조회: queryById("42", { topK: 11 })로 가장 가까운 11개를 받고, 자기 자신을 뺀 10개를 D1에서 조회해 점수 순서대로 돌려줍니다.
최종적 일관성(eventual consistency) Vectorize는 삽입 요청을 받은 뒤 몇 초가 지나야 검색에 반영됩니다. 그래서 방금 저장한 북마크로 곧바로 유사 조회를 하면 결과가 비어 있을 수 있습니다. 또한 삭제가 실패해서 Vectorize에 벡터가 남는 경우, 유사 조회 결과에 D1에 없는 ID가 섞일 수 있습니다. 그래서 D1을 조회할 때 존재하지 않는 ID는 조용히 버리도록 구현합니다.

교체 가능한 인터페이스

계획서의 이식성 요구에 따라, 코드의 나머지 부분은 Vectorize를 직접 호출하지 않고 아래 인터페이스만 사용합니다. 나중에 로컬 sqlite-vec이나 pgvector로 옮길 때는 이 인터페이스의 구현체 하나만 새로 작성하면 됩니다.

interface VectorStore {
  upsert(items: { id: number; vector: Float32Array }[]): Promise<void>;
  similar(id: number, k: number): Promise<{ id: number; score: number }[]>;
  delete(ids: number[]): Promise<void>;
}

5. API 엔드포인트

/api/* 경로는 모두 Authorization: Bearer <토큰> 헤더가 필요하고, 토큰이 틀리면 401을 돌려줍니다. 정적 페이지는 데이터를 담고 있지 않으므로 인증 없이 제공합니다.

메서드경로역할

GET/save저장 팝업 (정적 파일)

GET/api/bookmarks/lookup?url=이미 저장한 URL인지 확인 (팝업이 열릴 때 호출)
GET/api/bookmarks?q=&from=&to=&limit=&offset=키워드 검색과 날짜 필터. q가 없으면 최신순 목록
GET/api/bookmarks/:id북마크 하나의 상세 정보 (본문 포함)

6. 북마클릿과 팝업의 통신

팝업은 내 Worker 도메인에서 열리므로, 팝업이 보내는 API 요청은 같은 출처(same-origin) 요청이 됩니다. 따라서 CORS 설정이 전혀 필요 없습니다. 팝업 방식을 선택한 덕분에 CSP 문제와 CORS 문제가 함께 사라집니다.

다만 팝업이 로딩을 마치기 전에 데이터를 보내면 메시지가 유실되므로, 짧은 핸드셰이크를 거칩니다.

  1. 북마클릿이 현재 페이지에서 링크, 제목, description, 본문 앞부분을 추출합니다.
  2. 북마클릿이 window.open("https://<내 도메인>/save")로 팝업을 엽니다.
  3. 팝업이 로딩을 마치면 window.opener.postMessage("ready", "*")를 보냅니다.
  4. 북마클릿이 "ready"를 받으면 popup.postMessage(data, "https://<내 도메인>")로 데이터를 보냅니다. 수신자 출처를 내 도메인으로 지정하므로 다른 창이 데이터를 가로챌 수 없습니다.
  5. 팝업은 event.source === window.opener인지 확인한 뒤 데이터를 받아 화면에 채우고, lookup으로 중복 여부를 먼저 알려 줍니다.
  6. 사용자가 메모를 쓰고 저장을 누르면, 팝업이 localStorage에 보관한 토큰으로 POST /api/bookmarks를 호출합니다.
보안 측면 아무 사이트나 내 팝업을 열고 가짜 데이터를 보낼 수는 있습니다. 하지만 사용자가 직접 저장 버튼을 눌러야만 저장되고, 토큰은 내 도메인의 localStorage에만 있어서 다른 사이트가 읽을 수 없습니다. 혼자 쓰는 서비스에서는 이 정도로 충분합니다.

7. 파일 구조

vector/
├─ wrangler.jsonc            # D1, Vectorize, AI 바인딩, Cron, 정적 파일 설정
├─ migrations/
│  └─ 0001_init.sql          # 위 스키마
├─ src/
│  ├─ index.ts               # fetch()·scheduled() 진입점과 라우팅
│  ├─ auth.ts                # Bearer 토큰 검증 (상수 시간 비교)
│  ├─ time.ts                # Unix ms ↔ KST 변환
│  ├─ routes.ts              # /api/bookmarks 핸들러
│  ├─ db.ts                  # D1 쿼리 모음
│  ├─ embed.ts               # 입력 텍스트 조립 + Workers AI 호출
│  ├─ pipeline.ts            # pending → embedded → indexed 처리
│  └─ vector-store.ts        # VectorStore 인터페이스 + Vectorize 구현
├─ test/                    # node:test 단위 테스트 (npm test)
├─ scripts/
│  └─ smoke.sh               # wrangler dev 대상 API 흐름 검증
└─ public/
   ├─ index.html             # 검색 UI + 북마클릿 설치 링크
   └─ save.html              # 저장 팝업

파일 하나가 한 가지 역할만 맡도록 나눴습니다. 특히 db.ts와 vector-store.ts가 Cloudflare 전용 API를 감싸고 있으므로, 다른 환경으로 옮길 때 고쳐야 할 곳이 이 두 파일로 모입니다.

8. 무료 티어 예산

한도 수치는 현재 Cloudflare 문서를 기준으로 적었으며, 추후 바뀔 수 있습니다. 결론적으로 병목은 Vectorize 저장 한도(약 4,880개)이고, 나머지 자원은 개인 사용 규모에서 여유가 있습니다.

9. 확인한 사항

초안에서 임시로 정했던 세 항목을 아래와 같이 확정했고, 위 본문에도 반영했습니다.

  1. 본문 보관: content는 재임베딩용으로만 보관하고 키워드 검색에서는 제외합니다.
  2. 재시도 횟수 제한: 같은 단계에서 5회 연속 실패하면 Cron이 멈추고, 웹 UI에 "임베딩 실패"로 표시합니다. 이를 위해 embed_attempts 컬럼을 추가했습니다.
  3. 도메인: 보유한 도메인을 Worker에 연결합니다(Custom Domain). 나중에 다른 서버로 옮겨도 DNS만 바꾸면 북마클릿과 토큰을 그대로 쓸 수 있습니다. 구체적인 도메인 이름은 배포 단계에서 확인하겠습니다.

10. 구현 페이즈

구현은 다섯 페이즈로 나눕니다. 순서는 로컬에서 검증할 수 있는 것부터 정했습니다. D1은 로컬에서 완전히 흉내 낼 수 있지만, Workers AI와 Vectorize는 원격 자원이 필요하기 때문입니다. 그래서 2페이즈에서 D1만 쓰는 API를 먼저 완성해 두면, 3페이즈에서 문제가 생겼을 때 원인을 벡터 쪽으로 좁힐 수 있습니다.

각 페이즈는 한 번에 끝내지 않고 몇 차례에 나눠 진행하면서 중간 결과를 확인받습니다. 페이즈가 끝나면 docs/reports/에 변경 보고서와 퀴즈를 작성하고, 이 절의 상태를 갱신합니다.

API (D1만 사용)

다음

임베딩을 제외한 저장·조회·검색·삭제 API를 만들고, 로컬 wrangler dev에서 끝까지 검증합니다. 이 페이즈에서 저장한 북마크는 pending 상태로 남습니다.

파일
src/time.ts, src/auth.ts, src/db.ts, src/routes.ts, src/index.ts(라우팅 추가), .dev.vars.example, test/*.test.ts, scripts/smoke.sh
엔드포인트
POST /api/bookmarks, GET /api/bookmarks/lookup, GET /api/bookmarks(검색·날짜 필터), GET /api/bookmarks/:id, DELETE /api/bookmarks/:id(D1에서만 삭제). 유사 조회는 3페이즈에서 추가합니다.
진행 순서
  1. time.ts와 auth.ts: 외부 자원이 없는 순수 로직부터 작성합니다.
  2. db.ts: 2절 스키마에 맞는 행 타입과 SQL 함수를 작성합니다.
  3. routes.ts와 index.ts: 입력 검증, 응답 형식, 라우팅을 연결합니다.
  4. curl로 전체 흐름을 검증하고 보고서를 작성합니다.
완료 기준
  • 토큰이 없거나 틀리면 401, 정상 저장은 201, 같은 URL을 다시 저장하면 409와 기존 ID를 돌려줍니다.
  • content와 memo가 2,000자를 넘으면 잘라서 저장합니다.
  • 키워드 검색이 title·memo·description에서만 찾고, %·_가 들어간 검색어도 문자 그대로 찾습니다.
  • 날짜 필터가 KST 기준입니다. 예를 들어 UTC 2026-09-25T15:00Z에 저장한 행은 from=2026-09-26에 포함됩니다.
  • 응답의 created_at이 +09:00 문자열이고, 목록 응답에 embedding과 content가 들어가지 않습니다.
검증 방법
순수 함수(time.ts, auth.ts)는 Node 내장 테스트 러너로 단위 테스트합니다(npm test, 추가 의존성 없음). API 전체 흐름은 wrangler dev에 요청을 보내는 scripts/smoke.sh로 확인합니다.

벡터 파이프라인

예정

임베딩 생성, Vectorize 연동, 상태 전이, Cron 재시도, 유사 조회를 구현합니다. 이 페이즈부터 Cloudflare 계정이 필요합니다.

사전 준비
  • wrangler login으로 Cloudflare 계정에 로그인합니다.
  • 개발용 인덱스를 따로 만듭니다(예: bookmarks-dev, 1024차원, cosine). 로컬 D1의 ID와 운영 인덱스의 ID가 섞이지 않게 하기 위해서입니다.
  • wrangler.jsonc에서 AI와 Vectorize 바인딩을 원격 연결로 설정하고, 타입을 다시 생성합니다.
파일
src/embed.ts, src/vector-store.ts, src/pipeline.ts, src/index.ts(scheduled() 구현), src/routes.ts(유사 조회 추가, 저장 후 waitUntil, 삭제 시 Vectorize도 삭제)
완료 기준
  • 저장한 북마크가 pending → embedded → indexed로 전이하고, D1의 embedding이 정확히 4,096바이트입니다.
  • 유사 조회가 자기 자신을 뺀 결과를 점수 순서대로 돌려주고, D1에 없는 ID는 조용히 버립니다.
  • 임베딩 실패를 일부러 일으키면 embed_attempts가 늘어나고, 5회에 도달하면 Cron이 더 이상 시도하지 않습니다.
  • Cron을 수동으로 실행했을 때 밀린 항목이 처리됩니다.
  • 상태를 embedded로 되돌리는 SQL 한 줄로 Vectorize 재구축이 되고, 이때 Workers AI를 호출하지 않습니다.

5

배포

예정

운영용 원격 자원을 만들고, 보유한 도메인에 Worker를 연결해서 실제로 사용하기 시작합니다.

진행 순서
  1. wrangler d1 create vector-bookmarks로 원격 D1을 만들고, wrangler.jsonc의 임시 database_id를 실제 값으로 바꿉니다.
  2. npm run db:migrate:remote로 원격 D1에 스키마를 적용합니다.
  3. 운영용 Vectorize 인덱스 bookmarks를 만듭니다(1024차원, cosine).
  4. wrangler secret put API_TOKEN으로 운영 토큰을 등록합니다.
  5. wrangler.jsonc에 Custom Domain을 설정하고 npm run typecheck 후 npm run deploy를 실행합니다.
  6. 북마클릿의 도메인을 확정하고, 실제 사용 흐름과 Cron 실행 로그를 확인합니다.
완료 기준
  • 내 도메인에서 저장부터 유사 조회까지 전체 흐름이 동작합니다.
  • 매시간 Cron이 실행된 기록이 로그에 남습니다.
  • wrangler d1 export로 원격 D1을 SQL 파일로 내보내는 방법을 확인하고 문서에 남깁니다. 계획서의 "로컬로 쉽게 옮기기" 요구를 검증하는 단계입니다.
